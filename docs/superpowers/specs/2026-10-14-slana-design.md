## 1. Request and decisions

**What the user said (2026-10-14):**
- The game is called **Slana**. The logic changes: **large rooms, played 24/7**.
- Entering the rooms needs the token launched on pump.fun; **every room has a clear entry fee**; **everyone takes the tokens of whoever they eat**.
- **No money should leave the team; money should circulate between the users.**
- The NFTs will be the **main skins** and give access to the **Slana Pass**. The perks must come without money leaving the team. There will be rooms that cannot be played without an NFT (it varies room by room), and the NFT must have a **clear advantage**.
- The interface will be reworked from scratch and **freed from the "AI look"**. Animations and designs will be crafted with care.
- Matchmaking and the bot system will be tuned well. Documentation will be written.

**Decisions settled through questions:**

| Topic | Decision |
|---|---|
| NFT perks | Pass rooms + a lower fee + eligibility for season prizes + in-game power (the risks were explained, the user chose it knowingly) |
| Practice | Yes: free, no token, no NFT, with bots, no prizes |
| NFT chain / mint | Solana (Metaplex Core), **a free mint on our own mint page**; the NFTs trade on OpenSea/Magic Eden/Tensor. This route was chosen because OpenSea Studio does not support Solana mints. |
| NFT images | We design them (unique coin characters generated by the game's drawing code) |
| Token symbol | **$SLANA** (the mint address is entered once at setup) |
| Visual direction | **B · Paper Ticket** (risograph print; design canvas: https://claude.ai/artifact/3tFjCisE9AAC94Yw3w4SL8) |
| Earlier $SOGEL plan | Fully replaced by this document: there is **no** team-funded prize vault, no quests, no free-mode boosts and no SOL arenas |

**Assumptions (adjustable settings):** fee 5 % (Pass 2 %); split 50 % treasury / 30 % season / 20 % burn; Pass power +15 % start mass and a 2 s cash-out; collection supply 3,333, 1 mint per wallet; room fees are example values.

## 2. Through the player's eyes

1. Opens the site and plays **Practice** with bots, without a wallet and for free.
2. Connects a wallet. Buys $SLANA (pump.fun / DEX). Optionally makes a **Slana Pass application**: a free mint, network fee only.
3. In the lobby the rooms are listed as **admission tickets**: fee, player count, a "PASS" stamp, a Pass perk line.
4. Buys a ticket: one signature. The fee goes to the room's vault; their value in the game is this fee.
5. Plays. Takes the tokens of the players they eat. If a bot eats them, their tokens spill across the map as gold coins.
6. Cashes out with **C** whenever they like; a payout receipt is printed. The fee is taken from the profit, the rest arrives in their wallet.
7. A Pass holder collects season points. At the end of the season the top 10 share the pool filled by the players' fees.

## 3. Economy

### 3.1 Rooms (arenas)
- Every **arena** is an account on-chain. Fields: a fixed `entry_fee` (in $SLANA base units), `requires_pass`, `max_sessions` (cap on tickets open at once), `enabled`.
- An arena's vault is a token account owned by the arena PDA: `["vault", arena]`.
- The server runs **room instances (shards)** for every arena: at most **50 real players** per instance. When an instance is full, a new instance using the same vault opens.
- Paid rooms are open 24/7; bots play while they are empty. The map is **6400×6400**; the food and cactus counts scale with it.
- Default arenas (`pnpm admin create-arena --defaults`, amounts are examples):

| id | Name | Fee | Pass |
|---|---|---|---|
| 1 | Penny Pond | 1,000 $SLANA | not needed |
| 2 | Silver Creek | 10,000 $SLANA | not needed |
| 3 | Gold Lake | 50,000 $SLANA | required |
| 4 | Whale Bay | 250,000 $SLANA | required |

- `entry_fee` and `requires_pass` can only change while the arena has no open tickets.

### 3.2 Value flow (the in-game ledger)
- **Entry:** the player's value is `V = entry_fee`.
- **Eating:** when a cell is eaten, the proportional share of the value moves to the eater: `t = floor(V_victim · m_cell / M_victim)`. When the last cell is eaten, all the remaining value moves. This rule is kept exactly as in the existing ledger.
- **Bots are always worth 0:**
  - Eating a bot gives mass, not tokens.
  - If a bot eats a player's **last** cell, the player's remaining value turns into **loot coins** scattered at the point of death.
  - If a bot eats one of a player's cells, that cell's value share becomes loot.
- **Loot coins:**
  - The victim's value is split into `n = clamp(ceil(V / (entry_fee/4)), 3, 24)` pieces; the pieces add up to exactly `V`, the remainder is added to the first piece.
  - The pieces fly outward, slow down with friction and stay on the map; they never disappear by themselves.
  - Only **real players** can collect them; bots pass through them. The value of a collected piece is added to the collector's ledger.
- **Conservation (invariant):** for an arena, `Σ live values + Σ loot = vault balance − (pending payouts)`. A simulation test checks it.
- **Ejection (W), cactus pops, mass decay** do not change value.
- **AFK / disconnect:** the cell stays in the world for 45 s, then cashes out automatically. If the connection comes back, the player returns to their cell. This behaviour is kept from the existing code.
- **Session age:** the server cashes out automatically after at most 6 hours.

### 3.3 Cash-out and the fee
- A cash-out normally takes **3 s**, **2 s** on a Pass ticket; if you are eaten during it, you lose. The duration is a server setting.
- **The fee is taken only from profit:** `profit = max(0, payout − entry_fee)`. The rate is `fee_bps` (default 500 = 5 %); on a Pass ticket `pass_fee_bps` (default 200 = 2 %). Upper bound 1000 (10 %).
- The fee is split in three; the shares must add up to 10,000:
  - `treasury_bps` (default 5000): goes to the **treasury vault**. This is a token account owned by the program; the admin withdraws it with `withdraw_treasury`.
  - `season_bps` (3000): to the **season vault**.
  - `burn_bps` (2000): **burned** (leaves the token supply).
- Rounding: first `fee = floor(profit · bps / 10000)`, then the shares `floor(...)`; the remainder goes to the season vault. All arithmetic is overflow-checked.

### 3.4 The "no money leaves the team" rule

| Flow | Who pays |
|---|---|
| Ticket fee | The player |
| Session account rent (≈◎0.0017) | The player; **it returns to the player** when it closes |
| Network fee of the payout (settle) transaction | The player's ticket **deposit**: `settle_fee_lamports` (default 20,000 lamports ≈ ◎0.00002) is deposited into the session account on top of the rent; it moves to the server during the settle. The server wallet spends no net money. |
| Season prizes | The season vault filled by the players' fees |
| Losses caused by bots | Go back onto the map as loot (to the players) |
| Leftover of a closed arena | `sweep_arena` → the season vault (to the players) |
| NFT mint | The minter pays: Core asset rent + transaction fee |
| Remaining one-off costs | Program deployment rent, collection creation, arena/vault accounts, server hosting. These are infrastructure costs and are written in the docs. |

The team's income: the treasury share of the fee and the NFT secondary-sale royalty (the collection royalty plugin, default 5 %).

### 3.5 Seasons
- Season points come **only from games played with Pass tickets**: `session.has_pass` is recorded at the moment the ticket is bought. Points = the game's score (highest mass, capped).
- The season table is the top 20. When the season ends (`end_season`) the pool is frozen and the top 10 claim with these shares: 30 % / 20 % / 14 % / 10 % / 8 % / 6 % / 4.5 % / 3 % / 2.5 % / 2 %. The claim window is 30 days.
- What is not claimed moves to the active season with `rollover_season`.
- There is a single global season vault: `["season_vault"]`. Seasons keep their own pools as bookkeeping.
- **Invariant:** `Σ pending prizes + active pool ≤ season vault balance`.
- `fund_season` is removed: the team does not fund the pool.

### 3.6 Practice
- Fully off-chain: no token, NFT or wallet needed; no prizes, season points or chain records.
- The server keeps its own "Today / All time" tables; these tables are for practice and display only.
- **Leagues:**
  - **Rookie:** players below level 5 and players without a wallet. Bot mix 70 % easy, 30 % medium.
  - **Pro:** level 5 and above. The existing mix 45 %/40 %/15 %.
  - A player who goes over 3,000 mass or eats 8 players in one Rookie game is routed to Pro for 24 hours. This is kept in the server's memory, the signed session token or the IP.

## 4. Slana Pass (NFT)

### 4.1 Collection and free mint
- Standard: **Metaplex Core** (`CoREENxT6tW1HoK8ypY1SxRMZTcVPm7R94rH4PZNhX7d`).
- The collection's update authority is our program's PDA: `["pass_authority"]`. So only the program can mint.
- The admin script creates the collection: `pnpm admin create-collection --uri … --royalty-bps 500`. A Royalties plugin (recipient: the treasury owner) is added to the collection. Then `set_pass_collection` is called; this is done **once**, and the program checks that the collection really is a Core `CollectionV1` and that its authority is the PDA.
- The `mint_pass` instruction (anyone can call it):
  - **Conditions:**
    - the mint must be open (`pass_mint_open`, `pass_mint_start_ts`);
    - `pass_minted < pass_supply` (default 3,333);
    - per-wallet limit `pass_per_wallet` (default 1). The counter lives in the `["pass_minted", wallet]` PDA.
    - Optional bot filter: `pass_min_tokens` (default 0): the wallet must hold at least this much $SLANA.
  - **CPI:** Core `CreateV2` (discriminator `20`). The asset is a new keypair (the minter signs). Name `Slana Pass #<n>`, URI `pass_base_uri + n + ".json"`, owner the minter, collection our collection. `n = pass_minted + 1`, i.e. sequential.
  - **Price:** none. The minter pays the asset rent and the `pass_minted` PDA rent.
- **Fair distribution (commit–reveal):**
  - Before the mint opens, `pass_seed_hash = sha256(seed)` is written on-chain.
  - When the mint is over, the admin calls `reveal_pass(seed)`; the program checks the hash and publishes the seed.
  - The traits are computed with `traits(seed, n)`; nobody can know in advance which number is rare.
  - Before the reveal, every Pass shows as a "sealed passport" in the game and on the marketplaces.
- **Metadata hosting:** served by the game server by default:
  - `GET /pass/:n.json` and `GET /pass/:n.png`; before the reveal they return "sealed" content.
  - `GET /pass/collection.json`.
  - `pass_base_uri = https://<domain>/pass/`.
  - Images are generated on the first request with the NFT tool's drawing code and cached on disk.
  - The alternative for those who want to upload to Arweave is described in the docs.

### 4.2 Pass perks

| Perk | Where it is enforced |
|---|---|
| Entry to Pass rooms | **On-chain**: `join_arena` reads the Core asset (owner = the player, collection = ours); without it no ticket can be bought |
| 2 % fee | **On-chain**: `settle_session` uses `pass_fee_bps` when `session.has_pass` |
| Eligibility for season prizes | **On-chain**: points only from `has_pass` sessions |
| +15 % start mass, 2 s cash-out | **On the server**: when the session has `has_pass`. The values are adjustable (`PASS_START_MASS_MUL=1.15`, `PASS_CASHOUT_MS=2000`). The room ticket says it plainly: "Pass holders start +15 %, cash out in 2 s". |
| NFT as the main skin | **On the server**: ownership is verified, the traits are drawn in the game |

- **One NFT, one session:** when a Pass is used, `join_arena` creates the `["pass_lock", asset]` PDA. It closes on settle or refund and its rent returns to the player. A second ticket cannot be opened with the same NFT. Even if the NFT is transferred during a game, the new owner cannot use it until the lock is lifted.
- Using a Pass in a room without a Pass requirement is optional (`use_pass`). If it is used, the lock and the perks apply.

### 4.3 NFT visual system (traits)
Every Pass is a **risograph coin character** generated by the game's drawing code. The same code is used in the game, on the mint page and in the metadata image.

| Layer | Options (weights in the generator) |
|---|---|
| Ink (body) | 12 riso inks: Fluo pink, Teal, Mustard, Blue, Green, Orange, Purple, Red, Aqua, Lilac, Mint, Brown |
| Overprint (second colour) | 6 colours, offset direction/amount |
| Symbol (in the middle) | ◎, heart, star, bolt, moon, flower, crown, dollar, clover, diamond (vector) |
| Eyes | round, sleepy, star, wink, sunglasses, heart, determined, dizzy |
| Mouth | smile, grin, "o", tongue, cat, fang |
| Accessory | none, crown, cap, beanie, halo, propeller hat, headphones, party hat, cowboy, flower, laurel, horns |
| Paper (background) | cream, pink, mint, sky, butter, lilac |
| Special (Legendary) | gold-leaf rim, hologram, hand-made 1/1 (10 of them) |

- Rarity: Common / Rare / Legendary. Computed from the product of the weights; the thresholds are fixed in the generator.
- The same combination never appears twice (duplicates are weeded out).
- `traits(seed, n)` is deterministic: the server, the client and the generator use the same function from `packages/shared`.

## 5. Chain program `slana` (Anchor 1.2.1)

### 5.1 Token support
- `anchor_spl::token_interface`: **SPL Token and Token-2022**. All transfers use `transfer_checked`, burning uses `burn`.
- `initialize` validates the mint:
  - the token program must be one of the two;
  - there must be no `freeze_authority` (so the vault cannot be frozen);
  - for Token-2022 these extensions are **refused**: TransferFeeConfig, TransferHook, PermanentDelegate, NonTransferable, DefaultAccountState, ConfidentialTransferMint, Pausable. Metadata extensions are allowed.
- The mint address is written into the Config **once** and cannot change.

### 5.2 Accounts (PDA seeds)
- `Config ["config"]` (new fields):
  - authorities: `admin`, `server_authority`;
  - token: `token_mint`, `token_program`, `token_decimals`;
  - fee: `fee_bps`, `pass_fee_bps`, `treasury_bps`, `season_bps`, `burn_bps`, `settle_fee_lamports`;
  - general: `current_season`, `paused`;
  - collection and mint: `pass_collection` (`Pubkey::default` = not set), `pass_base_uri` (≤ 96 bytes), `pass_supply`, `pass_minted`, `pass_per_wallet`, `pass_min_tokens`, `pass_mint_open`, `pass_mint_start_ts`, `pass_seed_hash`, `pass_seed` (once revealed), `pass_revealed`;
  - counters and bumps.
- `TreasuryVault ["treasury_vault"]` and `SeasonVault ["season_vault"]`: token accounts with the Config PDA as authority.
- `PassAuthority ["pass_authority"]`: a signing PDA that holds no data.
- `PlayerProfile ["profile", owner]`: name, base skin, XP/level, games played, best score, season points (with the season id). A profile is required before a ticket; if needed the client sends `register_player` with `join_arena` in the same transaction.
- `Arena ["arena", id_u16_le]`: `id`, `entry_fee`, `requires_pass`, `max_sessions`, `open_sessions`, `enabled`, `vault`, counters.
- `ArenaVault ["vault", arena]`: a token account with the Arena PDA as authority.
- `Session ["session", arena, player]`: `id` (unique, from the Config counter), `player`, `arena`, `entry_fee`, `opened_at`, `has_pass`, `pass_asset` (default if none). Lamport balance = rent + `settle_fee_lamports`.
- `PassLock ["pass_lock", asset]`: `session`, `player`.
- `PassMinted ["pass_minted", wallet]`: `count`.
- `Season ["season", id_u32_le]`: top-20 table, `pool` (accumulated while active), `prize_pool` (when frozen), `claimed_mask`, `started_at`, `ended_at`, `finalized`.

### 5.3 Instructions
| Instruction | Signer | Summary |
|---|---|---|
| `initialize` | upgrade authority (ProgramData) | Config + vaults + season 1; mint validation |
| `update_config` | admin | fee/split (total 10000, fee ≤ 1000), `settle_fee_lamports` ≤ 1,000,000, paused, server, admin, Pass mint parameters (supply ≥ minted; the base URI does not change after the first mint) |
| `set_pass_collection` | admin | once; Core CollectionV1, authority = PassAuthority |
| `set_pass_seed_hash` | admin | before the first mint |
| `mint_pass` | minter + new asset keypair | 4.1 |
| `reveal_pass` | admin | sha256(seed) == hash; once |
| `create_arena` / `update_arena` | admin | 3.1; creates the vault account |
| `register_player` / `update_profile` | player | name (≤16 bytes UTF-8), base skin (0–7) |
| `join_arena(arena_id, use_pass)` | player | paused/enabled/capacity; `requires_pass` ⇒ use_pass; with a Pass, Core asset + create the PassLock; `transfer_checked` fee → vault; Session (+ deposit) |
| `settle_session(SettleArgs{session_id, payout, score, kills, xp})` | server | id match; `payout ≤ vault`; fee on profit (Pass rate); treasury/season/burn; payout → the player's token account; `settle_fee_lamports` → server; XP/stats; with a Pass, season points + table; the Session and the PassLock close (rent to the player) |
| `refund_session` | player | after 24 hours; `min(entry_fee, vault)`; all lamports including the deposit to the player |
| `end_season`, `claim_season_reward`, `rollover_season` | admin / winner / admin | 3.5; payouts in tokens |
| `sweep_arena` | admin | `enabled=false` and `open_sessions=0`: vault → season vault |
| `withdraw_treasury(amount)` | admin | treasury vault → the token account the admin gives |

- **Removed:** `buy_skin`, `record_game`, `fund_season`, SOL arenas.
- **Error codes:** the existing ones are kept, new ones are added: `MintNotAllowed`, `FreezeAuthorityPresent`, `PassRequired`, `PassNotOwned`, `PassWrongCollection`, `PassInUse`, `MintClosed`, `MintSoldOut`, `MintLimit`, `MintMinTokens`, `SeedMismatch`, `AlreadyRevealed`, `CollectionAlreadySet`, `BadSplit`, `ArenaBusy`, `BadBaseUri`.
- **Reading a Core asset** (by hand, without a dependency):
  - owner program = Core;
  - `data[0] == 1` (AssetV1);
  - `owner = data[1..33]`;
  - `data[33] == 2` (UpdateAuthority::Collection) and `data[34..66] == pass_collection`.
  - For the collection: `data[0] == 5` (CollectionV1) and `update_authority = data[1..33]`.

### 5.4 Tests (LiteSVM)
- Vault/session flows: separately with SPL Token and Token-2022 mints.
- Mint validation: a mint with a freeze authority and a mint with a transfer fee are refused.
- Pass gate: fake Core asset accounts are set up with `set_account`. Checks: wrong owner, wrong collection, lock conflict.
- Fee math (with / without a Pass, the burn lowers the supply), the settle deposit moving to the server.
- Refunds; an old payout cannot be applied to a reopened session (`session_id`).
- Season points only with a Pass, prize claims, rollover, arena sweep, treasury withdrawal.
- `mint_pass`: a real CPI if the Core program can be loaded into the test environment; if not, a unit test of the instruction data and account order + an end-to-end test on localnet with a cloned Core.

## 6. Game server

### 6.1 Rooms
- `RoomManager`: practice instances (`practice-rookie-N`, `practice-pro-N`, capacity 40) and arena instances (`arena-<id>-<n>`, 50 players).
- Arenas are read from the chain every 30 s; new arenas appear in the lobby by themselves.
- **Quick Play:** without a wallet or a balance it goes to practice; otherwise to the last arena played or to the cheapest arena the balance can afford. In the arena, the most crowded instance that is not full is chosen.
- Room info goes to the lobby as `RoomInfo`: `arenaId`, `entryFee`, `requiresPass`, instances, real player and bot counts, total loot ("X $SLANA on the floor").

### 6.2 Bots
- **Count:** in practice a target of 20 entities (min 4, max 20). In an arena a target of 24, min 2, max 16 bots. Bots retire as real players arrive.
- **In an arena:** bots are worth 0, do not collect loot, and carry a "BOT" tag.
- **Behaviour improvements:**
  - **Threat prediction:** the opponent's split range and velocity vector are taken into account.
  - **Cactus use:** hiding and shooting are kept.
  - **Loot avoidance:** bots do not target loot coins.
  - **Newcomer protection:** a real player is not attacked with a split for the first 25 s (existing rule).
  - **Opportunity chasing:** bots behave normally towards small real players; no excessive hunting. The share of easy bots depends on the league.
- Bot names and skins come from the base skin pool; only real players use the NFT look.

### 6.3 Loot and the journal
- **New entity type:** `EntityKind.Loot` (value + visual size).
- **Journal:** live ticket values and the loot list are written atomically per room:
  - whenever a payout is queued;
  - at least once a second when something changed.
- **Recovery:**
  - After a crash, live tickets are cashed out automatically (existing behaviour).
  - Loot is restored into the first instance of its arena.
  - Loot of an arena that was swept with `sweep_arena` or closed is discarded.

### 6.4 Chain gateway (SolanaChain v2)
- Token units (`decimals` read from the mint). Arena list: fee, Pass, capacity.
- `getSession` returns the new fields: `hasPass`, `passAsset`.
- **Payout worker:** the new `settle_session` accounts. On permanent errors (`SessionMismatch`, missing account) the item is dropped. On non-permanent errors it is retried.
- The **stale session sweeper** (15 min) is kept. The code for the `record_game` path is removed.
- **NFT verification:** `getAsset(address)`. The asset account is read (60 s cache): owner, collection, and `n` parsed from the `Slana Pass #n` name. If revealed, `traits(seed, n)`; if not, the sealed look.
- **List of owned Passes:** `GET /api/pass/owned?wallet=` (30 s cache).
  - If the RPC supports DAS, `getAssetsByOwner` (grouped by collection) is used.
  - Otherwise `getProgramAccounts` on the Core program: `memcmp` offset 1 = wallet, offset 34 = collection.
  - The client uses this list in the lobby and the skin picker. The server also re-verifies the single selected asset when entering a game.

### 6.5 Protection
- With a Pass, one ticket per wallet per arena and one session per NFT (on-chain).
- Rate limits on expensive messages: login, ticket, equipment (existing).
- Collusion detection is **not** in the scope of this version; it is written in the risks section.

### 6.6 Metadata endpoints
- `/pass/:n.json`, `/pass/:n.png`, `/pass/collection.json`, `/pass/collection.png`.
- Images are generated with `@napi-rs/canvas` on the first request and cached under `DATA_DIR/pass/`. Before the reveal the sealed image is returned.
- The endpoints are rate limited.

## 7. Web client — the "Paper Ticket" design system

### 7.1 Foundations
- **Colours:**
  - paper `#F1EADB`, card paper `#FFFCF4`;
  - ink `#1E1B2E`, secondary ink `#5D5870`;
  - fluo pink `#FF4F87` (`#D6245F` for text);
  - teal `#0E9C9A` (`#08716F` for text);
  - mustard `#F2B705` (`#8A6500` for text);
  - riso blue `#3B5BDB`, riso green `#1F9D61`, red `#E5402B`.
  - **Night print** (dark theme): paper `#1B1924`, ink `#F1EADB`, the same accents.
- **Type:** Bricolage Grotesque (headings and body; narrow width axis) and DM Mono (labels and numbers). Both are loaded locally through `@fontsource`.
- **Texture:** the paper grain comes from two layers of dot pattern and a light `feTurbulence`. Shadows are halftone dots.
- **Shapes:**
  - ticket (notch + perforation line), stamp (rotated framed text);
  - receipt (zigzag edge), passport (cover + page);
  - tape strips, newspaper columns and rules.
- **Icons:** ~32 custom SVG icons (2.2 px stroke, round caps). **No emoji in the interface**; emotes become drawn "stickers" too.

### 7.2 Screens
1. **Lobby / Tickets:**
   - masthead, wallet tag, season line (dateline);
   - the Pass card or a "Pass application" call;
   - ticket list: fee, Pass stamp, perk line, live counts, "X $SLANA on the floor";
   - Quick Play; bottom tabs on mobile.
   - The desktop layout is a newspaper front page: tickets on the left, the live room "photo" in the middle (the game's live view in a frame), the Pass and the standings on the right.
2. **Buying a ticket:** confirmation card (fee, fee rate, Pass perks, deposit note) → wallet signature → **stamp + ticket tear** animation → into the game.
3. **In-game screen (HUD):**
   - taped-on paper scraps: the till ("TILL 12,450 $SLANA", with a counter animation), the standings column, the minimap (sheet);
   - the cash-out button; receipt-printer progress; the event feed; emote stickers; the mobile joystick.
4. **Death:** the "EATEN" stamp, who ate you, the value lost, "New ticket" / "Practice".
5. **Cash-out receipt:** a receipt coming out of a printer (entry, gain, fee %, net) + a transaction link.
6. **Pass:**
   - **Pass holder:** passport view (NFT image, number, traits, perks, the session it is used in).
   - **Without a Pass:** the "Application" page (supply counter, a stamped mint button, a rotating trait preview).
   - **After the mint:** envelope opening / seal breaking (a sealed passport if not revealed) animation; OpenSea / Magic Eden / Tensor links.
7. **Standings (newspaper):** Season / Today / All time; pool; prize shares; claim.
8. **Profile:** name, level, stats, skin picker (base skins + owned Passes).
9. **Settings:** language, sound, theme, minimap, performance.
10. **Docs** (`/docs`): section 9.
11. **Spectator mode.**

### 7.3 Drawing the game world (risograph)
- **Floor:** paper + light-blue graph-paper squares + grain; the map border is a dashed line.
- **Coin characters:**
  - two-layer print: the body ink and a slightly offset second colour, `multiply`;
  - ink outline, halftone shadow;
  - the eyes follow the heading; expressions: hungry, scared, proud, sleepy.
  - The jelly stretch is kept.
- **Food:** riso confetti (dot, star, triangle). **Cactus:** spiky green riso. **Loot:** a mustard coin + a "$" stamp + sparkle.
- **Particles:** ink splatter, paper crumbs. A "click" stamp effect at the moment of eating.
- **Performance:** sprite cache; a 60 fps target with 120+ entities (mid-range laptop).

### 7.4 Motion rules
- **Durations:** micro-interactions 120–180 ms; screen transitions 260–360 ms (spring, with overshoot); stamp 420 ms (1.4 → 1 scale + 2–3° rotation + ink spread).
- **Patterns:**
  - buttons sink 3–4 px like a press;
  - numbers change by counting (a mechanical counter);
  - lists appear at 30 ms intervals;
  - on hover the pink layer shifts slightly.
- `prefers-reduced-motion`: loops stop, transitions shorten.

## 12. Risks and open issues
- **Law:**
  - A skill game played with a token of real value falls under gambling regulation in many countries.
  - Giving an NFT in-game power in a paid room can count as a "purchased advantage". This power is shown openly and can be turned off in the settings.
  - Season prizes and the burn must not be marketed as a "promise of returns".
- **Audit:** the program changed substantially (tokens, Core CPI, locks); an independent audit is needed before mainnet.
- **Program size:** `anchor-spl` and reading Token-2022 extensions make the program bigger. Estimated rent ≈ ◎4–6 (recoverable); the exact value is written into the docs after the build.
- **Core program on localnet:** cloning from mainnet needs network access. Without it, tests use fake assets, a unit test is written for `mint_pass` and the real mint is tried on devnet.
- **Collusion (two wallets feeding each other):** no countermeasure in this version. Behaviour analysis can be added later.
- **Free mint and bots:** there is a per-wallet limit and an optional `$SLANA` holding requirement. No full sybil protection.
- **Hosting the metadata on the server:** if the server goes down, the images on the marketplaces disappear. A guide to moving to Arweave is provided to prevent this.
